CURSOR AI BUILD INSTRUCTIONS — All 11 Simulations (No Docker)

## Purpose

This file is a single-stage, end-to-end developer instruction set intended for Cursor AI (or a developer using Cursor) to build a full replication of MSgames.in with **11 simulations** in one project. It deliberately **omits containerization and Docker** (per request). The instructions cover repository layout, environment setup, database schema, backend and frontend frameworks, real-time architecture, job queues, reporting, and a per-simulation implementation blueprint.

## High-level choices (already decided)

* Frontend: Next.js (React) + Tailwind CSS
* Backend: Node.js (Express) — clear JS/TS ecosystem and easy Socket.io integration
* Realtime: Socket.io
* Primary DB: PostgreSQL
* Cache / short-term state: Redis
* Job Queue: BullMQ (Redis based)
* Storage: AWS S3 (presigned URLs)
* PDF/Charts server-side: Puppeteer + Chart.js (node-canvas)
* Email: AWS SES / SendGrid
* Hosting (no Docker): Backend — Render/Railway/Heroku; Frontend — Vercel; DB — Supabase/RDS; Redis — Upstash/Redis Cloud

## Real-time architecture

* Namespace-per-simulation: `/ws/:simulationSlug`
* Room-per-session: `session:{sessionId}`
* Events: `join_session`, `player_action`, `state_update`, `round_end`, `leaderboard_update`, `session_end`
* Use Redis adapter for Socket.io when deploying multiple backend instances

## Game engine pattern

Each simulation implements a shared interface (class skeleton):

```
class BaseEngine {
  constructor(sessionConfig){}
  applyAction(playerId, action){}
  advanceRound(){}
  computeMetrics(){}
  getPublicState(){ return serializableState }
}
```

Store session's authoritative in-memory state in Redis (for fast access), and periodically persist snapshots to Postgres.

## Session lifecycle

1. Facilitator creates session (POST /sessions) with configuration JSON
2. Backend generates sessionCode, creates DB session, initial Redis state
3. Participants join with code (via WebSocket join or REST join)
4. Gameplay proceeds by rounds. Decisions are sent via `player_action` socket events
5. Engine applies actions, computes consequences, emits `state_update`
6. At session end, worker generates reports (PDF/Excel), stores to S3, and sends notifications

## Reporting pipeline

1. Collect raw data from DB / Redis snapshot
2. Compute derived metrics (game-specific)
3. Render chart PNGs with Chart.js on Node using node-canvas
4. Render HTML report template (Handlebars/EJS) with PNG embedded
5. Puppeteer generate PDF from HTML
6. Upload PDF to S3 and save DB row
7. Send email with presigned URL

## Job processing

* Use BullMQ with Redis. Jobs: `generateParticipantReport`, `generateFacilitatorReport`, `bulkZipExport`
* Workers run on backend (or a dedicated worker dyno) and execute report generation

## Frontend structure (Next.js)

* Pages: /, /login, /dashboard, /sessions/create, /sessions/:id, /join
* Game pages: /games/:slug/play?session=ID
* Components: common (Navbar, Modal), dashboard, facilitator tools, game-specific components
* Real-time: use a `useSocket` hook to connect to correct namespace/room
* State: small local state for UI; global store (Redux/Zustand) for session state and syncing

## Deployment without Docker

* Frontend: Deploy to Vercel (connect to GitHub repo) — automatic builds
* Backend: Deploy to Render or Railway — set env variables, build command `npm run build && npm start`
* PostgreSQL: Use Supabase or RDS (set connection string on render)
* Redis: Use Upstash / Redis Cloud (connection via env)
* Workers: Run as separate render service (same repo, different start command `node dist/workers.js`)
* Domain + CloudFront: Use AWS Route53 + CloudFront if needed

## Testing & QA

* Unit tests: Jest for backend services
* Integration: Playwright for E2E UI flows (session creation, join, gameplay)
* Load testing: k6 for socket load simulation (simulate 100 concurrent players per session)

## Security

* Use HTTPS everywhere (Render/Vercel provide TLS)
* Store JWT secret in env
* Use parameterized queries (ORM handles) to prevent SQL injection
* CSRF protection on REST forms
* Rate-limits on endpoints (express-rate-limit)

## Per-simulation replication blueprint (developer tasks)

General approach: Build a common scaffolding (sessions, participants, sockets, report pipeline) and then implement each simulation engine as a pluggable module (service). Each engine has: initialConfig, stepLogic, scoring logic, serializer, visualization data provider.

1. Fruit Beer Game — Supply chain (4-tier)

* Data: customer demand timeline, lead time, inventory per tier, orders pipeline
* Engine: weekly rounds, demand generator, order fulfillment logic, pipeline handling
* Key functions: generateDemand(), receiveShipments(), fulfillOrders(), placeOrders()
* Reports: bullwhip analysis, time-series inventory charts, cost breakdown

2. TOC Simulation — Factory manager

* Data: 5 machines config, processing times, setup times, products A/B
* Engine: DBR scheduling, prioritize constraint, release material based on drum
* Key functions: scheduleBatches(), processMachineQueues(), identifyBottleneck()
* Reports: machine utilization, throughput, bottleneck heatmap

3. Order Ops — Food delivery (real-time)

* Data: restaurants, drivers, orders, map coords
* Engine: continuous event generator (orders), driver assignment algorithm, routing delays (simplified)
* Key functions: assignDriver(), simulateDriverMovement(), computeDeliveryCost()
* Realtime: use frequent `state_update` emits to update map markers
* Reports: avg delivery time distribution, cost per delivery, fleet utilization

4. HR Compensation (To Pay or Not to Pay)

* Data: candidates, market benchmarks, stakeholder templates
* Engine: stage-based (valuation -> evaluation -> negotiation), scoring rules as defined
* Key functions: evaluateSalaryScore(), scoreCandidateFit(), rankCorrelation()
* Reports: attribute weights vs correct, ranking Spearman rho, final compensation breakdown

5. Sustainable Select (MADM)

* Data: alternatives, attributes, expert ratings
* Engine: implement WSM, WPM, TOPSIS, MOORA, entropy/CRITIC weighting
* Key functions: normalizeMatrix(), applyWeights(), computeTOPSIS()
* Reports: method-wise rankings, variance analysis, sensitivity charts

6. Onion Dilemma — Game theory supply chain

* Data: players (FC/RC), trust indices, market conditions
* Engine: simultaneous decisions per round, payoff matrix, trust update rules
* Key functions: calculatePayoff(), updateTrustIndex(), botStrategy implementations
* Reports: payoff evolution, trust index timeline, equilibrium identification

7. Dual Source Dilemma — Procurement

* Data: two suppliers (parameterized costs, lead times), cash ledger, demand pattern
* Engine: periodic ordering decisions, pipeline arrivals, cash accounting and borrowings
* Key functions: generateDemand(), placeOrderToSupplier(), processArrivals(), computeCash()
* Reports: final bank balance, service levels, supplier mix

8. Defect Detectives — Quality control

* Data: defect logs, shifts, process params
* Engine: sequential application of QC tools (check sheet -> histogram -> pareto -> fishbone -> scatter -> flowchart -> control chart)
* Key functions: analyzeDefectFrequency(), buildPareto(), computeControlChartStats()
* Reports: before/after control charts, root cause analysis, defect reduction percent

9. Customer in a Store — Stock-flow cognitive

* Data: inflow/outflow time series, participant responses
* Engine: present variations per group type (learning-by-doing, decomposition, binary feedback), detect correlation heuristic
* Key functions: calculateStock(), detectHeuristic(), adaptiveQuestionSelection()
* Reports: accuracy, improvement rate, heuristic detection

10. EV Gambit — Strategy (Porter)

* Data: company status, industry events per round, decision options
* Engine: round events modify forces, player picks decisions, compute market share and profit outcomes
* Key functions: applyEventImpact(), computeMarketShare(), simulateCompetitorReaction()
* Reports: market share trend, event impact analysis

11. Order Ops variants, additional games

* Reuse Order Ops engine variant components where necessary

## Developer tasks per simulation (concrete)

For each simulation implement in this order:

1. DB schema migrations (game-specific tables)
2. Engine class in `services/gameEngine/{slug}Engine.ts`
3. REST endpoints: create session (/sessions), join (/sessions/:id/join), get state (/sessions/:id/state)
4. Socket handlers: `websocket/handlers/{slug}Handler.ts` (listen `player_action`, call engine.applyAction)
5. Frontend page `frontend/src/pages/games/{slug}.tsx` with components for all stages
6. Reporting provider for visualization data
7. Tests: unit tests for engine logic and integration tests for REST + Socket

```ts
const app = express();

const io = new Server(server, { cors: { origin: '*' } });

io.of('/ws/fruit-beer').on('connection', (socket) => {
  socket.on('join_session', ({sessionId, userId}) => {
    socket.join(`session:${sessionId}`);
  });
  socket.on('player_action', async (payload) => {
    // validate, apply via engine
  });
});

server.listen(process.env.PORT || 4000);
```
